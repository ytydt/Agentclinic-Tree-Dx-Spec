结论：**不要只依赖 CPG 构造“鉴别诊断知识图谱”**。CPG 通常强调诊疗推荐和流程，不一定系统枚举“临床表现相近疾病”。更稳妥的路线是：

**CPG / CKS / specialty guidelines 提供高置信诊断流程与排除项；HPO / Orphanet / UMLS / SNOMED / PrimeKG 提供疾病—表型—概念标准化；EHR、病例库、合成诊断数据集提供共现、问诊路径和验证集。**

## 1. 应优先抽取哪些关系

建议把 KG 设计成“疾病—表现—鉴别依据—检查—证据来源”的结构，而不是简单的 disease–symptom 共现图。

| 关系类型 | 示例 |
|---|---|
| `disease_has_manifestation` | 肺炎 → 发热、咳嗽、胸痛 |
| `disease_similar_to / differential_diagnosis` | 肺炎 ↔ 肺栓塞、心衰、哮喘急性发作 |
| `finding_discriminates_for` | 突发胸痛 + D-dimer 升高 → 支持肺栓塞 |
| `finding_discriminates_against` | 无发热、CRP 正常 → 相对不支持感染 |
| `red_flag_for` | 神经定位体征 → 中枢神经系统病变警示 |
| `recommended_test_for_differentiation` | 胸痛鉴别 → ECG、肌钙蛋白、D-dimer、CTPA |
| `diagnostic_criterion` | SLE、RA、心衰、糖尿病等标准化诊断条件 |
| `risk_factor / epidemiology / time_course` | 年龄、性别、职业暴露、病程急慢性 |
| `provenance` | 指南来源、发布日期、章节、证据等级、推荐强度、许可 |

## 2. CPG / 指南类数据源：从哪里拿，开放性如何

| 数据源 | 适合抽取什么 | 开放性与限制 |
|---|---|---|

| **CDC** | 感染病、公共卫生疾病、case definition、检测指征、暴露史 | CDC/ATSDR 网站大多数内容为美国政府公共领域，可自由使用和复制，但仍需逐项确认页面版权说明。citeturn516311search1 |
| **WHO Guidelines** | 全球公共卫生、感染病、母婴、慢病、低资源场景诊疗建议 | WHO 内容通常以 **CC BY-NC-SA 3.0 IGO** 形式允许非商业复用，商业或模型训练场景需谨慎核查。citeturn516311search2 |
| **MAGICapp / GRADE-based guidelines** | 结构化推荐、PICO、evidence profile、decision aid | MAGICapp 支持结构化指南、证据摘要和 API 发布，适合 computable guideline；但具体指南内容的版权和 API 权限取决于发布方。citeturn516311search7 |
| **IDSA、ESC、EULAR、ACR、AAP 等专科指南** | 专科疾病诊断标准、检查路径、鉴别诊断、严重程度分层 | 很多可公开阅读，但大规模抽取、再分发、商业使用通常受版权约束；适合“证据核验源”，不一定适合作为开放 KG 的原始语料。 |
| **AWMF 德国指南库** | 德语高质量 CPG，尤其适合德国/欧洲医疗语境 | AWMF 指南注册库公开，但版权通常归作者组或专业学会，使用协议需要单独确认；AWMF 正在推进数字化指南接口和标准。citeturn583695search9turn583695search3turn583695search11 |
| **EPFL / Meditron Clinical Guidelines Corpus** | 大规模英文 CPG 文本预处理语料，适合启动抽取管线 | 该语料收集 46,649 篇 CPG，公开释放 35,733 篇，来自 CCO、CDC、CMA、ICRC、NICE、SPOR、WHO、WikiDoc 等允许再分发的来源；但 WikiDoc 等众包内容质量需额外过滤。citeturn770238view6 |
| **GGPONC 德语肿瘤指南语料** | 德语 oncology CPG、证据等级、推荐信息 | GGPONC 是基于肿瘤临床实践指南的可自由分发德语语料，不含患者数据，适合德语医学 NLP/KG。citeturn583695academia32 |

**实务判断：** 如果目标是开放发表或开源 KG，优先使用 **CDC、WHO、EPFL redistributable subset、GGPONC、HPO、Orphanet、PrimeKG、Mondo、部分 PubMed/PMC 文献**。如果只是内部研究验证，可加入 NICE、专科指南、商业知识库，但必须保留许可边界。

## 3. 非 CPG 但非常关键的数据源

| 数据源 | 作用 | 开放性 |
|---|---|---|
| **HPO** | 标准化症状/体征/表型词表；非常适合统一“临床表现”节点 | HPO 提供人类疾病表型异常标准词表，并有 OMIM 等疾病注释文件可下载。citeturn615347search6turn615347search22 |
| **Orphanet** | 罕见病—临床表现—HPO 表型映射 | Orphanet 提供罕见病临床描述，并用 HPO 术语描述临床体征/症状。citeturn296994search2turn296994search14 |
| **Mondo Disease Ontology** | 疾病 ID 归一化、跨 OMIM/Orphanet/DO/SNOMED 等映射 | Mondo 目标是协调全球疾病定义，适合做 disease normalization。citeturn296994search20 |
| **UMLS** | 医学概念统一、同义词、跨词表映射 | UMLS 需要 UMLS Metathesaurus License 和 UTS 账号；NLM 不收费，但其中 SNOMED CT 等源词表可能有地域性许可限制。citeturn615347search0turn615347search4 |
| **SNOMED CT** | 临床概念标准化，适合 EHR 对齐 | SNOMED 在成员国使用通常不收费，非成员地区可能需要年度许可费用。citeturn615347search5turn615347search9 |
| **PrimeKG** | 现成多模态医学 KG，含 disease–symptom、disease–disease 等关系 | PrimeKG 整合 20 多个高质量来源，并包含 Mayo Clinic、Orphanet、DrugBank 等临床描述扩展；适合作为开放 KG 的 backbone。citeturn615347search7turn945818view0 |
| **MIMIC-IV / MIMIC-IV-ED / MIMIC-IV-Note** | EHR 病例、主诉、诊断、病程记录，可用于验证“表现—诊断”关系 | 去标识化、研究访问受控；MIMIC-IV 覆盖 65,000+ ICU 患者和 200,000+ ED 患者，并可与 ED、Note、CXR 等模块链接。citeturn493881view1 |
| **DDXPlus** | 合成病例 + differential diagnosis + 症状/既往史 | Figshare 发布，CC BY 4.0；但其底层知识来自 proprietary medical KB 和商业规则系统。citeturn493881view2 |
| **MedDialog / doctor-patient consultation datasets** | 问诊文本、症状表达、诊断任务评测 | 多数适合模型评测和问诊路径学习，但诊断标签质量、许可和隐私需逐项审查。 |

## 5. 推荐的数据源组合

如果目标是构造一个**可发表、可复现、尽量开放**的临床诊断 / 鉴别诊断 KG，我建议采用以下栈：

**第一层：标准化实体层**

使用 **Mondo / Disease Ontology** 统一疾病节点，使用 **HPO** 统一症状、体征和表型节点，使用 **UMLS / SNOMED CT** 做同义词、临床术语和 EHR 对齐，但注意 UMLS 和 SNOMED 的许可限制。

**第二层：开放疾病—表型 backbone**

用 **HPO annotations、Orphanet、PrimeKG、Open Targets clinical signs/symptoms** 建立 disease–phenotype、disease–disease、rare disease phenotype 关系。PrimeKG 尤其适合作为初始 KG backbone。

**第三层：CPG / guideline 证据层**

优先抓取 **CDC、WHO、EPFL Clinical Guidelines Corpus、GGPONC、部分 MAGICapp guideline**；NICE、AWMF、专科学会指南可作为高质量核验源，但再分发和训练使用要谨慎。

**第四层：鉴别诊断增强层**

从 NICE CKS、医学教材 decision trees、综述文章、case reports、MIMIC-IV-Ext-DiReCT、DDXPlus、MedDialog / DxBench 等数据中抽取：

`疾病 A 与疾病 B 表现相近`  
`区分 A/B 的关键症状、体征、实验室、影像、病程、危险因素`  
`下一步推荐检查`  
`红旗征象 / 排除条件`

**第五层：人工审校与版本控制**

每条关键鉴别关系都应保存 provenance：来源、章节、句子、发布日期、证据等级、抽取模型、人工审核状态。临床 KG 最危险的错误不是漏掉边，而是把“共现关系”误当成“诊断依据”。

---

最核心的判断是：**CPG 给你“应该怎么诊断”，HPO/Orphanet/PrimeKG 给你“疾病和表现怎么标准化连接”，EHR/病例数据给你“真实场景中怎么出现”，而真正的鉴别诊断 KG 需要把三者融合，并额外显式建模 discriminating features。**

## 总体判断

现有研究并没有一个完全成熟、开放、CPG-only 的 **“综合征入口 → 鉴别疾病组” KG**。最接近的组合是：

**DDXPlus / chief complaint datasets**  
负责提供 `chief complaint / syndrome → candidate disease group` 的结构。

**Diagnostic schemas / textbook decision trees / DiReCT**  
负责提供 `综合征内如何分层鉴别`，例如 dyspnea → pulmonary / cardiac / metabolic / neuromuscular。

**CPG corpus / NICE / CDC / WHO / PubMed guidelines**  
负责提供 `red flags、recommended tests、diagnostic criteria、rule-in/rule-out features`。

**PrimeKG / HPO / Orphanet / Mondo / UMLS / SNOMED CT**  
负责标准化实体与补充 disease–symptom、disease–disease、phenotype–disease backbone。

**MIMIC-IV-ED / MIMIC-IV-Note / MedDialog / HumanDx**  
负责校验真实世界中 `主诉 → 实际诊断分布 → 问诊路径`。

如果你的目标是开源或可发表，我建议把 KG 分成三层：  
**syndrome/chief complaint layer → differential disease group layer → discriminating evidence layer**。其中 syndrome layer 可参考 DDXPlus 和 diagnostic schema；disease/evidence layer 用 PrimeKG、HPO、Orphanet、guidelines 和 MIMIC/病例数据补强。

**方案 C：罕见病综合征入口优先**

以 **HPO + Orphanet HOOM + PubCaseFinder** 为核心，构建 `phenotype set → rare disease group → discriminating phenotype/gene/test`。这个方向开放性最好，但病种范围偏罕见病。citeturn593914view3turn362035view4

如果你的目标是一般临床诊断，而不是仅罕见病，我会建议把成品设计为：  
**`syndrome/chief complaint layer` 自建，`disease–phenotype backbone` 复用 PrimeKG/HPO/HOOM，`diagnostic evidence layer` 从指南和高质量综述抽取。**

## 1. CPG / guideline 抽取路线：从“诊疗推荐”转成“诊断流程图”

这一类路线从 **clinical practice guidelines、诊疗路径、专家经验** 中抽取诊断节点、检查节点、判断条件和最终疾病类别。代表性资源是 **MIMIC-IV-Ext-DiReCT**：其数据集说明中明确提到，作者为 25 个疾病类别构建 diagnostic knowledge graph，每个 subgraph 记录某类疾病的 diagnostic procedure，并以 JSON 保存，构建依据包括 existing guideline 和 physician experience。citeturn635477search1

另一类基础语料是 **EPFL / Meditron Clinical Guidelines Corpus**，它收集了约 46K 篇 clinical practice guidelines，并公开释放了来自 CCO、CDC、CMA、ICRC、NICE、SPOR、WHO、WikiDoc 等可再分发来源的子集。citeturn396203search0

这条路线适合抽取：

```text
综合征/表现 → 初步分层 → 推荐检查 → 排除条件 → 可能疾病类别
```

优点是**证据等级较高、临床可解释性好**。缺点是 CPG 往往围绕单病种或治疗路径组织，不一定天然提供“胸痛 → 心源性 / 肺源性 / 消化道 / 肌骨骼”等 syndrome-entry 结构。

## 2. Diagnostic schema / 医学教材路线：从“临床推理框架”构图

这是最贴近你目标的一条路线。医学教育中的 **diagnostic schema** 本来就是连接 **problem representation** 和 **differential diagnosis generation** 的结构化临床知识框架。相关综述明确将 diagnostic schemas 定义为连接问题表征与鉴别诊断生成的桥梁。citeturn396203search3

这条路线的数据源通常包括：

```text
医学教材章节
临床推理教学材料
diagnostic schema 图
clinical decision tree
case-based teaching materials
```

抽取出的 KG 更像：

```text
acute dyspnea
  → cardiac causes
      → heart failure
      → ACS
      → arrhythmia
  → pulmonary causes
      → pneumonia
      → pulmonary embolism
      → asthma/COPD exacerbation
  → metabolic / toxic / neuromuscular causes
```

优点是**天然支持综合征入口和疾病大类分层**。缺点是：教材、教学图谱、schema 往往版权受限；许多研究只能在论文中描述构建方法，不一定开放完整图谱。

## 3. 症状检查器 / 合成病例路线：从 automatic diagnosis 数据集中反推 DDx KG

这条路线最容易得到规模化数据。典型例子是 **DDXPlus**。DDXPlus 是一个大规模合成 automatic symptom detection / automatic diagnosis 数据集，包含 ground-truth pathology、symptoms、antecedents 和 differential diagnosis；其 Figshare 页面说明患者由 proprietary medical knowledge base 和商业 rule-based automatic diagnosis system 合成，并以 CC BY 发布数据集。citeturn635477search2 DDXPlus 论文也强调其约 130 万合成患者包含 differential diagnosis、真实疾病、症状和 antecedents。citeturn635477academia53

在此基础上，**MedRAG** 进一步发布了面向 DDXPlus 的 diagnostic knowledge graph；其仓库说明称该 KG 用于基于 manifestations 的诊断和治疗推荐，尤其针对 clinical manifestations 相似的疾病。citeturn635477search0 MedRAG 论文摘要中还描述了一个 four-tier hierarchical diagnostic KG，用于包含不同疾病之间的关键诊断差异。citeturn635477academia54

这条路线的 KG 形态通常是：

```text
patient manifestation / chief complaint
  → symptom set
  → possible pathology
  → differential diagnosis list
  → distinguishing manifestations
```

优点是**结构化程度高、规模大、容易训练模型**。缺点是合成数据依赖隐藏的 proprietary medical KB，临床证据来源不可完全追溯；因此适合作 prototype 和 benchmark，不适合作最终高可信临床知识源。

## 4. EHR / 急诊主诉路线：从真实病历中学习表现—疾病关联

这一类工作直接从 EHR 中学习疾病—症状关系。经典代表是 Rotmensch 等人的 **Learning a Health Knowledge Graph from Electronic Medical Records**，目标是从电子病历自动学习 linking diseases and symptoms 的知识库。citeturn714046search0 相关开源仓库称其 Health KG 覆盖 157 个疾病和 491 个症状，来自 270,000+ 患者数据。citeturn714046search12

MIMIC-IV-ED 也常作为这类路线的数据源。它包含约 425,000 次急诊就诊，提供 vital signs、triage information、medication reconciliation、medication administration 和 discharge diagnoses。citeturn714046search6

典型抽取流程是：

```text
EHR notes / triage / chief complaint
  → clinical concept extraction
  → disease code normalization
  → symptom–disease co-occurrence / conditional probability
  → disease–symptom weighted graph
```

优点是**真实世界分布强**，可以发现 textbook/CPG 中不显著但临床常见的共现关系。缺点也很关键：EHR 图谱通常学习的是统计关联，不能直接等同于“鉴别诊断依据”。例如“发热—肺炎”是强关联，但“发热如何区分肺炎、尿路感染、脑膜炎、风湿免疫病”还需要额外建模。

## 5. 医学本体 / 多源 KG 路线：先建标准化 disease–phenotype backbone

这条路线不是直接从综合征入口构图，而是先解决 **实体标准化、同义词、跨数据库映射、疾病—症状 backbone**。

代表资源包括 **PrimeKG**。PrimeKG 整合 20 个高质量生物医学资源，描述 17,080 个疾病和 4,050,249 条关系，覆盖多个生物医学尺度。citeturn635477search3 它适合作为 disease–symptom、disease–disease、drug–disease 等关系的底座。

另一类是 **UMLS / SNOMED CT 路线**。DR.KNOWS 使用 UMLS-based KG，并将其接入 LLM 做诊断预测。citeturn714046search1 其论文摘要也明确说 KG 来自 UMLS，用于自动诊断生成。citeturn714046search25

HPO 则提供标准化人类表型异常词表。HPO 官方说明其提供 human disease 中 phenotypic abnormalities 的 standardized vocabulary。citeturn396203search5 Orphanet HOOM 进一步把 rare disease 与 HPO 表型连接，并可带 frequency、diagnostic criterion、pathognomonic sign 等附加信息。citeturn396203search2

这条路线通常抽取：

```text
disease ↔ phenotype
disease ↔ disease
phenotype ↔ synonym / parent / child
disease ↔ ontology ID
finding ↔ SNOMED / UMLS CUI
```

优点是**标准化能力强、可复用性好**。缺点是它不是原生 DDx KG；需要你额外生成：

```text
syndrome → candidate disease group
disease pair → discriminating feature
finding → rule-in / rule-out
```

## 6. 罕见病 phenotype-driven DDx 路线：从表型集合到候选疾病

这条路线在罕见病领域最成熟。数据源通常包括：

```text
HPO
Orphanet / HOOM
OMIM
Mondo / MedGen
PubMed case reports
rare disease phenotype annotations
```

HPO 与 Orphanet 已经形成较强协同，HPO 下载页说明 Orphanet 正在用 HPO terms 重新标注其疾病条目。citeturn396203search1 HOOM 则提供 rare disease–HPO 表型注释，并可加入 frequency、diagnostic criterion、pathognomonic sign。citeturn396203search2

这条路线的 KG 形态是：

```text
phenotype set
  → ranked rare diseases
  → key positive / negative phenotypes
  → gene / inheritance / confirmatory test
```

它非常适合：

```text
发育迟缓 + 癫痫 + 特殊面容 → 遗传综合征 DDx
多系统表型组合 → 罕见病候选排序
```

但对普通急诊综合征，比如胸痛、腹痛、呼吸困难、发热，覆盖不足。

近年还有一条新路线：先从医学百科、疾病库或在线资料构造 disease database，再用 LLM 生成病例和诊断链。**Chain-of-Diagnosis / DiagnosisGPT** 就属于这一类；其论文说明用 disease encyclopedias 生成 synthetic patient cases 和 CoD training data。citeturn714046search11 GitHub 项目也说明 CoD 旨在提升 medical diagnostics for LLMs 的可解释性。citeturn714046search3

这类路线通常产生：

```text
case presentation
  → possible diseases
  → confidence distribution
  → next symptoms to ask
  → diagnostic chain
```

优点是**数据生成效率高、适合训练推理模型**。缺点是医学百科质量参差不齐，LLM 生成链条可能引入幻觉；因此更适合做训练/评测辅助，而不是直接作为权威 DDx KG。

## 总结：现有研究的核心分歧

现有工作大致可以分成两类：

**一类从临床权威知识出发**：CPG、diagnostic schema、教材、专家经验。  
它们更接近真正的鉴别诊断逻辑，但规模化和开放性差。

**另一类从数据规模出发**：EHR、DDXPlus、MedDialog、医学百科、LLM 合成病例。  
它们更容易形成大规模图谱，但需要再补充证据等级、鉴别依据和人工校验。

对于你要构建的 **“综合征入口 → 需鉴别诊断的几类疾病”** KG，我建议采用组合路线：

```text
Diagnostic schema / CPG
  → 定义 syndrome-level 框架和疾病大类

DDXPlus / MedRAG-DDXPlus KG / MIMIC-IV-ED
  → 补充症状入口、候选疾病分布、真实场景表达

PrimeKG / HPO / HOOM / UMLS / SNOMED CT
  → 做实体标准化和 disease–phenotype backbone

Guidelines / reviews / case reports
  → 抽取 discriminating features、red flags、recommended tests

专家审校
  → 将共现关系升级为可用的鉴别诊断关系
```

最实用的工程路径是：**先用 schema/CPG 定义顶层综合征分类，再用 DDXPlus/EHR 扩展候选疾病，再用 HPO/PrimeKG 标准化实体，最后用指南和专家审校补充 rule-in / rule-out / test recommendation。**

## 1. 为什么不是“综合征”作为主入口

“综合征”有三个问题：

第一，**粒度不稳定**。同一个病例可以被归入“呼吸困难”“急性低氧”“休克”“感染综合征”“心肺综合征”等多个入口，召回边界会高度依赖人工命名。

第二，**不够贴合真实检索系统**。现有 DDx 系统更常采用“findings + patient context”输入，而不是先让用户选择综合征。例如 Isabel 要求输入 demographics 和 presenting clinical features，复杂病例也可以输入 lab、imaging、co-morbidities、risk factors；VisualDx 的 differential diagnosis builder 也是输入 findings 和 patient context 后生成 ranked possibilities。citeturn762678view3turn762678view4

第三，**综合征标签会掩盖区分性信息**。临床推理文献强调 problem representation：它不是原始症状堆叠，而是把具体症状、体征转化为带语义限定词的临床问题表述；这个步骤位于数据采集和假设生成之间，并触发 plausible diagnoses。citeturn762678view1

所以，“综合征”可以保留为一个**中间语义标签**，例如 acute hypoxemic respiratory failure、subacute monoarthritis、fever with rash，但不宜作为主检索键。

## 2. 最合适的检索入口：本次就诊问题表征

我建议主入口命名为：

**Episode-level Problem Representation，简称 EL-PR。**

它的核心不是“病人有什么异常”，而是：

> **在本次就诊中，哪些证据共同定义了当前需要解释的主问题？**

它应包含 5 类信息：

| 层级 | 内容 | 作用 |
|---|---|---|
| **A. 主问题锚点** | 主诉、主要症状、时间进程、解剖部位、系统定位 | 限定检索空间 |
| **B. 语义限定词** | acute/subacute/chronic，focal/diffuse，progressive/intermittent，pleuritic/non-pleuritic，febrile/afebrile 等 | 把原始表现转成可推理表征 |
| **C. 显著阳性证据** | 新发或明显异常的生命体征、实验室结果、影像 finding、体征 | 召回候选疾病和疾病大类 |
| **D. 显著阴性证据** | 关键阴性症状、阴性检查、影像未见某异常 | 排除或降权候选诊断 |
| **E. 背景修饰因子** | 年龄、性别、妊娠、免疫状态、药物史、基础病、危险因素 | 改变先验概率，不直接等同于主病因证据 |

临床推理中的 illness script 通常包括流行病学、时间进程、关键症状体征、诊断检查和治疗等要素；这说明最自然的检索对象不是 syndrome node，而是把病例 evidence profile 与疾病 illness script 匹配。citeturn762678view2

## 4. 为什么“显著证据画像”比“综合征入口”更稳

现有公开资源和系统形成了一个共同趋势：

**症状检查器 / DDx 系统**  
DDXPlus 不是从综合征标签出发，而是从 patient evidence 出发：每个合成患者包含 symptoms、antecedents、ground-truth pathology 和 differential diagnosis。citeturn762678view6

**罕见病 DDx 系统**  
PubCaseFinder 采用 HPO phenotype-driven retrieval，本质是从一组 phenotype findings 到疾病排序，而不是从综合征标签到疾病。citeturn105678search3

**EHR / ED 数据资源**  
MIMIC-IV-ED 提供 ED stays、triage、vital signs、medication reconciliation、diagnoses 等，天然支持“本次就诊 episode-level evidence”建模，而不是 syndrome-label 建模。citeturn762678view10

**FHIR / 数据标准**  
FHIR Observation 覆盖生命体征、实验室、影像结果、临床体征等；DiagnosticReport 则承载 laboratory、pathology、imaging report 及其上下文。这说明工程层面也更适合把输入建成 observation/report-level evidence profile。citeturn762678view8turn762678view9

**影像文本抽取**  
RadGraph 这类资源把放射报告转成 entities and relations，用于从自由文本报告中抽取结构化 finding。citeturn762678view7

这些资源共同指向：**最佳入口是“结构化病例表现画像”，不是“综合征标签”。**

## 5. 推荐的检索架构

我建议采用三阶段检索，而不是单入口检索。

### 第一阶段：主诉 / 主问题粗召回

用主诉和问题表征的核心词做 broad recall：

```text
acute dyspnea
acute chest pain
fever with altered mental status
abdominal pain with hypotension
new focal neurologic deficit
```

这一阶段目标是**不漏掉大类**，例如：

```text
急性呼吸困难
→ cardiac
→ pulmonary
→ metabolic
→ neuromuscular
→ toxicologic
→ hematologic
```

但这只是粗召回，不做最终排序。

---

### 第二阶段：显著 evidence profile 精排

用结构化证据进行匹配和降权：

```text
vitals
labs
imaging findings
exam findings
time course
risk factors
medications
key negatives
```

此时匹配的是疾病 illness script 或 diagnostic schema，而不是 syndrome node。

例如：

```text
acute dyspnea + hypoxemia + unilateral leg swelling + elevated D-dimer + clear CXR
→ pulmonary embolism 上升

acute dyspnea + fever + productive cough + lobar opacity
→ pneumonia 上升

acute dyspnea + orthopnea + elevated BNP + pulmonary edema
→ heart failure 上升
```

---

### 第三阶段：疾病对 / 疾病组之间的鉴别证据检索

当候选疾病组已形成后，再检索：

```text
PE vs pneumonia
heart failure vs COPD exacerbation
ACS vs aortic dissection
sepsis vs adrenal crisis
stroke vs seizure/Todd paresis
```

这一步需要 KG 里显式建模：

```text
disease_pair → discriminating_feature
disease_pair → recommended_test
disease_pair → rule_in_feature
disease_pair → rule_out_feature
disease_pair → red_flag
```

这比直接从综合征入口找疾病更可靠。

---

## 6. 如何处理“无关主病因的基础病异常值”

这是关键。你的输入里有病史、药物史、人口学、检验和影像，但存在很多与主病因无关的异常值。因此系统必须先做 **salience filtering**，否则 KG 检索会被慢性异常污染。

我建议每个 finding 都打 6 个标签：

| 标签 | 含义 |
|---|---|
| `episode_related` | 是否与本次主诉同一时间窗出现 |
| `new_or_changed` | 是否新发、恶化，或较本人 baseline 明显变化 |
| `severity` | 异常程度是否足以解释当前问题 |
| `specificity` | 对某些疾病是否有区分力 |
| `explained_by_background` | 是否可被已知基础病或长期用药解释 |
| `diagnostic_role` | rule-in、rule-out、risk modifier、background、noise |

然后将证据分成三类。

### A. 主病因候选证据

用于强检索和排序：

```text
新发低氧
急性肌钙蛋白升高
新发肺叶实变
突发局灶神经缺损
严重低钠伴意识改变
```

### B. 背景修饰因子

用于改变先验概率或治疗约束，但不直接作为主病因召回依据：

```text
慢性肾病
长期房颤
糖尿病
慢性贫血
长期激素使用
免疫抑制
抗凝药使用
```

### C. 噪声 / 附带异常

除非与本次主诉有时间或机制连接，否则低权重：

```text
CKD 患者长期肌酐升高
稳定慢性贫血
老年人长期轻度白蛋白低
慢性肝病患者长期轻度凝血异常
既往影像已存在的陈旧性病灶
```

一句话：**异常值不等于显著证据；显著证据 = abnormal + new/changed + temporally aligned + mechanistically coherent + discriminative。**

## 7. KG 中应建立哪类入口节点

我建议不要建立单一 `syndrome` 节点作为 root，而是建立以下几类 root / index node：

| 节点类型 | 是否作为主入口 | 示例 |
|---|---:|---|
| `chief_problem` | 是，粗召回 | chest pain, dyspnea, fever, syncope |
| `problem_representation` | **是，主入口** | acute pleuritic chest pain with hypoxemia |
| `semantic_qualifier` | 是，辅助 | acute, chronic, focal, diffuse, exertional |
| `salient_finding_set` | **是，主入口** | hypoxemia + tachycardia + clear CXR + elevated D-dimer |
| `diagnostic_schema` | 是，召回对象 | acute dyspnea schema |
| `illness_script` | 是，召回对象 | pulmonary embolism script |
| `syndrome` | 否，辅助索引 | acute coronary syndrome, nephrotic syndrome |
| `disease` | 否，目标节点 | pulmonary embolism, pneumonia |
| `disease_group` | 是，候选层 | cardiac causes, pulmonary causes, metabolic causes |

最核心的检索路径应是：

```text
episode-level problem representation
  → diagnostic schema / disease group
  → illness scripts
  → disease candidates
  → pairwise discriminating evidence
```

## 8. 推荐的数据标准化方案

你的输入证据建议这样归一化：

| 原始证据 | 建议标准化 |
|---|---|
| 主诉 / 症状 / 体征 | SNOMED CT / UMLS / HPO，另保留原文 |
| 生命体征 | FHIR Observation + LOINC/SNOMED |
| 实验室 test | LOINC for test identity，SNOMED/UCUM for value/unit/interpretation |
| 影像文本 | RadGraph / RadLex / SNOMED finding |
| 病史 / 基础病 | SNOMED CT / ICD / OMOP Condition |
| 药物史 | RxNorm / ATC |
| 人口学 | FHIR Patient / OMOP Person |
| 时间关系 | onset、duration、trend、before/after medication、before/after symptom onset |

LOINC 和 SNOMED CT 的配合在实验室和临床观测中很常见；FHIR Observation 也明确覆盖 vitals、laboratory data、imaging results、clinical findings 等。citeturn329971search1turn762678view8

## 9. 最终建议

你的系统中，**最合适的检索入口不是“综合征”，而是：**

> **本次就诊问题表征 EL-PR + 显著证据画像 Salient Findings Profile。**

更具体地说：

```text
chief complaint
+ time course
+ semantic qualifiers
+ salient positive findings
+ salient negative findings
+ demographics/risk modifiers
+ medication/context modifiers
+ baseline-adjusted abnormal findings
```

再通过它检索：

```text
diagnostic schema
→ disease group
→ illness script
→ differential disease candidates
→ pairwise discriminating features/tests
```

这样设计的好处是：

1. **比 syndrome 更细**，能表达 acute/subacute、局灶/弥漫、进展/波动、伴随/不伴随等语义。
2. **比 symptom list 更稳**，能过滤无关基础病异常值。
3. **比 disease-first 更符合鉴别诊断流程**，先召回疾病组，再区分疾病。
4. **与现有资源兼容**，可以接入 DDXPlus、MIMIC-IV-ED、FHIR Observation、RadGraph、HPO、PrimeKG、UMLS/SNOMED、CPG/diagnostic schema。
5. **可显式建模噪声**，把 chronic baseline abnormality 作为 context，而不是误当成主病因证据。

最简洁的工程结论是：

> **用“主诉”做粗入口，用“问题表征”做主入口，用“显著证据画像”做排序入口，用“疾病对鉴别证据”做解释入口。**

# 2. 如何避免 RAG 候选池被常见疾病挤占

不要使用单一向量检索：

```text
query = 病例文本
top-k documents = 向量相似度最高
```

这会天然偏向：

```text
常见病
长文档
高频术语
指南覆盖多的疾病
embedding 上语义近但临床不特异的疾病
```

应该改成 **multi-channel stratified candidate recall**。

---

## 推荐第一阶段召回结构

```text
Patient evidence bundle
  ├─ channel 1: chief complaint / ED distribution recall
  ├─ channel 2: salient finding / HPO-SNOMED phenotype recall
  ├─ channel 3: lab-pattern recall
  ├─ channel 4: imaging-finding recall
  ├─ channel 5: medication / exposure / demographic recall
  ├─ channel 6: rare-disease recall
  ├─ channel 7: critical-miss / cannot-miss recall
  └─ channel 8: guideline-schema recall
          ↓
  quota-based candidate fusion
          ↓
  candidate disease groups + disease candidates
```

核心原则：**每个 channel 有自己的 top-k quota**。

例如：

| Channel | top-k quota |
|---|---:|
| Chief complaint / ED common disease | 20 |
| Salient findings phenotype match | 30 |
| Lab pattern | 15 |
| Imaging pattern | 15 |
| Rare disease / HPO-Orphanet | 25 |
| Critical-miss diagnoses | 15 |
| Medication / exposure related | 10 |
| Guideline schema disease groups | 10 |

这样即使“肺炎、心衰、COPD、ACS、UTI”等常见病相似度很高，也不能把罕见病、危急病、检查驱动疾病全部挤出。

---

# 3. 推荐的粗召回排序策略

第一阶段不要输出唯一排名，而应输出 **分层候选池**。

## 3.1 先 group-level，再 disease-level

先召回疾病组：

```text
acute dyspnea
→ cardiac
→ pulmonary
→ vascular
→ infectious
→ metabolic
→ toxicologic
→ neuromuscular
→ hematologic
→ rare/genetic
```

再在每组内召回具体疾病：

```text
pulmonary vascular
→ pulmonary embolism
→ pulmonary hypertension crisis
→ diffuse alveolar hemorrhage
→ pulmonary veno-occlusive disease
```

这样可以避免 disease-level common diagnoses 过早垄断。

---

## 3.2 区分 recall score 和 final diagnostic score

第一阶段只负责“不漏”，不负责“最可能”。

建议保留 4 个分数：

```text
recall_score        证据匹配强度
prior_score         年龄、性别、患病率、场景先验
acuity_score        不可漏诊程度
rarity_guard_score  长尾保护分
```

第一阶段候选池用：

```text
candidate_inclusion_score
= max(channel_score)
+ critical_miss_boost
+ rare_channel_boost
+ evidence_specificity_boost
```

最终诊断排序才引入：

```text
posterior_likelihood
= evidence_match
× epidemiologic_prior
× temporal_coherence
× baseline_adjustment
× negative_evidence_penalty
```

也就是说，**患病率 prior 不能在第一阶段过强使用**，否则罕见病永远进不了候选池。

---

## 3.3 用 diversity / MMR / cluster quota

同一疾病簇不要占满候选池。例如胸痛病例中，如果 top-20 全是 ACS 相关变体，系统就失败了。

应设置：

```text
每个 pathophysiologic group 最多 N 个
每个 organ system 最少 M 个
rare-disease channel 至少 R 个
cannot-miss diagnoses 强制保留
```

例如胸痛：

```text
cardiac ischemic: max 5
aortic/vascular: max 4
pulmonary: max 5
GI: max 4
MSK: max 3
toxic/metabolic: max 3
rare/high-risk: min 3
```

## 3.4 对罕见病使用“单独索引 + 后融合”

罕见病不要和常见病共用同一个 vector store top-k。

建议建立：

```text
index_common_ed
index_guideline_schema
index_phenotype_hpo
index_rare_orphanet
index_lab_pattern
index_imaging_pattern
index_medication_adverse_event
index_critical_miss
```

然后用 **reciprocal rank fusion / weighted fusion / quota fusion** 合并。关键是：**rare_orphanet index 的 top-k 先进入候选池，再参与后续 rerank**。

# 7. 关键工程策略

## 第一，RAG 检索单位不要是“整篇指南”

更好的 chunk 单位是：

```text
diagnostic criterion
red flag
rule-in feature
rule-out feature
recommended initial test
recommended confirmatory test
disease-vs-disease distinguishing feature
illness script section
```

否则长指南会支配检索结果。

---

## 第二，候选疾病先召回，再为每个候选找证据

普通 RAG 是：

```text
case → documents → answer
```

你这个任务应改成：

```text
case → candidate diseases/groups → candidate-specific documents → answer
```

这样罕见病只要进入候选池，就有机会在第二阶段被检索和解释。

---

## 第三，建立 cannot-miss diagnosis index

对某些主诉，必须强制召回危急病，即使概率不高。

例如：

```text
chest pain
→ ACS
→ aortic dissection
→ pulmonary embolism
→ tension pneumothorax
→ esophageal rupture

headache
→ SAH
→ meningitis/encephalitis
→ cerebral venous sinus thrombosis
→ temporal arteritis
→ intracranial mass

abdominal pain
→ AAA rupture
→ ectopic pregnancy
→ mesenteric ischemia
→ perforation
→ bowel obstruction
```

这是临床安全层，不应完全交给向量相似度。

---

## 第四，基础病异常值必须进入 salience classifier

例如：

```text
CKD 患者肌酐 2.1
长期贫血 Hb 10
慢性房颤
长期影像陈旧纤维灶
```

这些不能直接作为主病因召回强特征。应标记为：

```text
background_context
baseline_abnormality
risk_modifier
treatment_constraint
```

只有当它们满足：

```text
new_or_changed
temporally_aligned
mechanistically_coherent
severity_sufficient
```

才升级为主病因证据。

# 1. 先定义“一阶段诊断方向”是什么

不要把一阶段方向定义成：

```text
肺炎
肺栓塞
心衰
COPD
贫血
焦虑
```

这样会很快变成 disease-level 列表，被常见病挤占。

更合适的是定义为：

```text
本次主问题的可解释病理生理方向
```

例如“急性呼吸困难”不是直接召回疾病，而是先召回：

```text
airway obstruction / ventilation failure
parenchymal gas-exchange disorder
pulmonary vascular disorder
cardiac pump / ischemic / rhythm disorder
oxygen-carrying capacity disorder
metabolic acidosis / increased respiratory drive
neuromuscular / central drive failure
toxicologic / medication-related cause
functional / panic-related dyspnea
artifact / measurement issue
```

然后每个方向再映射疾病：

```text
pulmonary vascular disorder
→ pulmonary embolism
→ pulmonary hypertension crisis
→ pulmonary veno-occlusive disease
→ tumor emboli
```

这样做的好处是：**第一阶段保证方向覆盖，第二阶段再做疾病排序。**

---

# 2. 完备性：用“方向本体 + 残差桶 + 覆盖测试”保证

## 2.1 不要依赖文档召回自然产生完备性

普通 RAG 的 `top-k document retrieval` 无法保证完备。它会偏向常见病、长文档、高频术语和 embedding 相似度高的内容。第一阶段应该检索一个**预定义方向空间**，而不是让候选方向从文档中自然涌现。

方向本体应从以下资源构建：

| 资源类型 | 用途 |
|---|---|
| diagnostic schema / clinical reasoning materials | 定义主问题到诊断方向的框架 |
| CPG / CKS / guidelines | 补充 red flags、检查路径、不能漏诊方向 |
| EHR / ED 数据 | 验证真实世界主诉覆盖 |
| HPO / SNOMED / UMLS | 标准化 finding 和疾病概念 |
| MIMIC-IV-ED / DDXPlus | 验证 chief complaint 到候选疾病组的召回覆盖 |
| PrimeKG / HPO / Orphanet | 补充 common + rare disease backbone |

临床推理文献中，problem representation 和 diagnostic schema 正是从病例特征到 differential diagnosis 的桥梁；语义限定词用于把原始临床特征抽象成可推理的问题表征。citeturn569543search1turn569543search14

---

## 2.2 每个主问题都要有固定的方向模板

例如：

```text
acute dyspnea template
chest pain template
fever template
abdominal pain template
altered mental status template
syncope template
acute weakness template
jaundice template
acute kidney injury template
anemia template
rash + fever template
```

每个模板下面固定包含若干方向。模板不是综合征标签，而是**problem representation 的粗入口**。

例如“发热”方向模板可以包括：

```text
localized bacterial infection
systemic viral infection
opportunistic infection
inflammatory / autoimmune disease
malignancy / paraneoplastic fever
drug fever / toxicologic cause
thromboembolic / ischemic inflammation
endocrine / metabolic hyperthermia
postoperative / device-associated infection
travel / zoonotic / exposure-related infection
factitious / measurement artifact
```

这比“感染综合征”更完整，因为它显式留出了非感染性发热、药物热、肿瘤热、血栓相关炎症、测量假象等方向。

---

## 2.3 必须设置残差方向

完备性不能只靠已知分类。每个模板都应包含：

```text
other / not otherwise classified
multisystem disease
iatrogenic / medication-related
pregnancy- or sex-specific cause
immunocompromised-host cause
rare / genetic / congenital
artifact / measurement error
coexisting secondary process
```

这些 residual buckets 的作用不是最终诊断，而是防止系统过早把异常解释进常见路径。

---

## 2.4 用覆盖测试验证完备性

建立一个 gold / silver test set：

```text
MIMIC-IV-ED chief complaint cases
DDXPlus synthetic cases
NEJM CPC / clinicopathological cases
PubMed case reports
rare disease HPO cases
local retrospective cases
expert-written adversarial cases
```

每个病例至少标注：

```text
chief problem
true diagnosis
true disease group
expected first-stage direction
cannot-miss directions
rare-disease direction required or not
```

一阶段评估不要看 top-1 accuracy，而要看：

```text
direction recall@K
disease-group recall@K
critical-miss recall@K
rare-disease channel recall@K
coverage by organ-system group
coverage by pathophysiologic mechanism
```

例如：

```text
目标：
direction recall@10 ≥ 0.98
critical-miss recall@K = 1.00
rare-disease recall@K 单独评估
```

# 3. 互斥性：不要要求全局互斥，要做“分区内互斥”

临床方向天然会重叠。例如：

```text
sepsis
→ infection
→ inflammatory response
→ shock
→ metabolic derangement
→ organ dysfunction
```

如果强行要求所有方向全局互斥，反而会错误。

正确做法是：**把方向拆成多个正交分区，每个分区内尽量互斥，分区之间允许多标签。**

## 3.1 建议使用四个正交分区

### 分区 A：主导解剖系统

```text
cardiovascular
pulmonary
neurologic
gastrointestinal / hepatobiliary
renal / urinary
hematologic
endocrine / metabolic
infectious / immune
toxicologic / medication-related
obstetric / gynecologic
musculoskeletal / soft tissue
psychiatric / functional
multisystem
artifact
```

### 分区 B：主导病理生理机制

```text
vascular / ischemic
infectious
inflammatory / autoimmune
neoplastic
mechanical / obstructive
degenerative
metabolic / endocrine
toxic / medication-induced
traumatic
genetic / congenital
functional
iatrogenic
artifact
```

### 分区 C：时间进程

```text
hyperacute
acute
subacute
chronic
acute-on-chronic
recurrent / episodic
progressive
intermittent
```

### 分区 D：临床风险层级

```text
immediately life-threatening
urgent but stable
common benign
rare but high-impact
background / incidental
```

一个方向不再是单个标签，而是一个 tuple：

```json
{
  "problem": "acute dyspnea",
  "system": "pulmonary",
  "mechanism": "vascular",
  "time_course": "acute",
  "risk_tier": "cannot_miss"
}
```

这对应的疾病组才是：

```text
pulmonary embolism spectrum
pulmonary hypertension crisis
diffuse pulmonary vascular disease
```

这样既能保持分区内互斥，又允许复杂病例跨分区表达。

---

## 3.2 疾病可以多标签，方向必须有 primary assignment

疾病本身允许属于多个方向：

```text
SLE
→ autoimmune
→ renal
→ neurologic
→ hematologic
→ pulmonary
```

但在某个具体 episode 中，必须指定 primary explanatory direction：

```text
本次就诊：急性胸痛 + 低氧 + D-dimer 高
SLE 背景存在，但 primary direction 可能是 pulmonary vascular / PE
```

因此 KG 中要区分：

```text
disease_static_membership
episode_primary_direction
episode_secondary_modifier
background_comorbidity
```

SNOMED CT 这类术语系统本身也区分 clinical finding、procedure、situation with explicit context、events 等层级；因此工程上应避免把“疾病、发现、上下文状态”混成一个平面标签。citeturn569543search3turn569543search9

# 4. 证据可分性：为每个方向建立“判别证据矩阵”

一阶段方向必须满足一个条件：

> 每个方向至少有一组可以与其他方向区分的 evidence slots。

也就是说，方向不是随便命名的；如果两个方向没有可区分证据，就应该合并。

---

## 4.1 建立 direction × evidence matrix

每个主问题模板都建立矩阵：

```text
rows    = diagnostic directions
columns = evidence features
values  = support / oppose / neutral / required / cannot-miss
```

例如急性呼吸困难：

| Evidence | Airway obstruction | Parenchymal lung | Pulmonary vascular | Cardiac | Metabolic |
|---|---:|---:|---:|---:|---:|
| wheezing | ++ | + | 0 | + | 0 |
| focal consolidation | 0 | ++ | - | 0 | 0 |
| clear CXR + hypoxemia | 0 | - | ++ | + | 0 |
| elevated BNP + pulmonary edema | 0 | + | 0 | ++ | 0 |
| severe metabolic acidosis | 0 | 0 | 0 | 0 | ++ |
| unilateral leg swelling | 0 | 0 | ++ | 0 | 0 |
| pleuritic chest pain | 0 | + | ++ | 0 | 0 |
| chronic neuromuscular disease | + | 0 | 0 | 0 | + |

这张矩阵就是“证据可分”的核心。

---

## 4.2 每个方向必须有四类证据槽

每个 direction 至少要定义：

```text
rule-in features
rule-out / against features
discriminating tests
missing evidence to ask/order
```

例如：

```json
{
  "direction": "pulmonary vascular acute dyspnea",
  "rule_in": [
    "acute dyspnea",
    "pleuritic chest pain",
    "tachycardia",
    "hypoxemia with relatively clear chest imaging",
    "unilateral leg swelling",
    "recent immobilization"
  ],
  "rule_out_or_against": [
    "alternative clear focal pneumonia explaining hypoxemia",
    "normal definitive vascular imaging"
  ],
  "discriminating_tests": [
    "D-dimer in appropriate pretest probability context",
    "CT pulmonary angiography",
    "lower limb venous ultrasound",
    "echocardiographic RV strain if unstable"
  ],
  "common_competing_directions": [
    "parenchymal lung infection",
    "cardiac failure",
    "airway obstruction"
  ]
}
```

检验和影像证据必须标准化。FHIR Observation 可表示生命体征、实验室、影像结果等原子观测，DiagnosticReport 用于组织检验、病理、影像报告并引用 Observation；LOINC 是用于健康测量、观察和文档的国际术语标准。citeturn569543search4turn328579search3

影像文本应先转为结构化 finding，而不是直接把整段报告塞进向量检索。RadGraph 就是面向放射报告的实体与关系抽取 schema；其原始数据集含专家标注报告，并释放了大规模自动标注的 MIMIC-CXR 报告实体和关系。citeturn328579search2turn328579search14

## 4.3 用信息增益或方向间 margin 判断“可分”

每个 evidence feature 对方向的区分力可以估计为：

```text
IG(feature; direction)
LR+ / LR-
direction-specificity
coverage
negative-evidence utility
```

工程上可用一个简单判据：

```text
如果某两个方向在 evidence vector 上长期高度相似，
且没有可靠的 discriminating test，
则不应在第一阶段拆成两个方向。
```

例如：

```text
viral bronchitis vs early mild pneumonia
```

在第一阶段可以同属：

```text
infectious lower respiratory tract disease
```

第二阶段再用影像、炎症指标、病程、严重程度细分。

相反：

```text
pulmonary embolism vs pneumonia
```

应在第一阶段分开，因为它们的关键证据和检查路径不同。

# 5. 一阶段方向本体的构建流程

推荐按下面步骤做。

## Step 1：从主问题模板开始，而不是从疾病开始

先列出高频主问题：

```text
chest pain
dyspnea
fever
abdominal pain
headache
altered mental status
syncope
acute weakness
jaundice
edema
AKI
anemia
rash
seizure
back pain
```

每个主问题建立 direction template。

---

## Step 2：用病理生理机制生成候选方向

对每个主问题，先按机制枚举：

```text
vascular
infectious
inflammatory
neoplastic
mechanical / obstructive
metabolic / endocrine
toxic / medication-related
traumatic
genetic / congenital
functional
artifact
```

这一步确保“病因类别”不漏。

---

## Step 3：用 cannot-miss 列表补齐危急方向

例如胸痛必须保留：

```text
ACS
aortic dissection
pulmonary embolism
tension pneumothorax
esophageal rupture
pericardial tamponade
```

即使当前证据弱，也应进入第一阶段候选池。

---

## Step 4：用 rare / long-tail 通道补齐低频方向

例如：

```text
acute intermittent porphyria
pheochromocytoma crisis
TTP
HLH
adrenal crisis
vasculitis
mitochondrial disease
inborn errors of metabolism
```

这些不能和常见病共用同一个 top-k。要通过 HPO、Orphanet、case reports、rare disease index 单独召回。HPO 提供人类疾病表型异常的标准化词表，并包含大量遗传病注释；这类资源适合做 phenotype-driven long-tail recall。citeturn569543search5

---

## Step 5：用真实病例和合成病例做覆盖回归测试

每次修改方向本体或召回逻辑，都跑：

```text
common ED cases
rare disease cases
critical-miss cases
multi-morbidity cases
baseline-abnormality noise cases
adversarial cases
```

确保新版本没有把某些方向挤掉。

# 6. 如何处理基础病异常值，避免破坏证据可分性

你的场景里，很多异常值不一定属于本次主病因。这会直接破坏方向分离。

因此 evidence 不能只有 abnormal/normal，还要有 salience 状态：

```text
episode_salient
baseline_abnormal
risk_modifier
treatment_constraint
explained_by_known_condition
possible_complication
noise_or_artifact
```

例如：

```text
CKD 患者肌酐 2.1
```

不能自动强召回：

```text
acute kidney injury / uremia / renal failure direction
```

除非它满足：

```text
new_or_worse_than_baseline
temporally_aligned_with_chief_problem
severity_sufficient_to_explain_current_problem
mechanistically_coherent
```

更合适的标记是：

```json
{
  "finding": "creatinine 2.1",
  "status": "baseline_abnormality",
  "diagnostic_role": "context_modifier",
  "retrieval_weight": "low_for_primary_direction",
  "use_cases": [
    "contrast risk",
    "drug dosing",
    "background risk",
    "comorbidity prior"
  ]
}
```

# 8. 形式化约束：把“完备、互斥、可分”写进系统规则

## 8.1 完备性约束

```text
For each chief_problem_template:
  returned_directions must cover:
    - at least one common direction
    - all applicable cannot-miss directions
    - at least one rare/long-tail guard if phenotype complexity is high
    - medication/toxic direction if medication/exposure evidence exists
    - artifact/background direction if evidence inconsistency exists
```

## 8.2 互斥性约束

```text
Within each partition:
  one evidence item may support multiple directions,
  but each direction must have one primary system and one primary mechanism.

Across partitions:
  multi-label is allowed.
```

## 8.3 证据可分性约束

```text
For every pair of retained directions:
  there must exist at least one discriminating feature or test,
  unless the pair is explicitly marked as inseparable_at_stage_1
  and deferred to stage_2.
```

## 8.4 候选融合约束

```text
No single disease family may occupy more than N slots.
Each high-level mechanism receives a minimum quota if evidence-compatible.
Rare/cannot-miss channels bypass common-disease competition.
```

# 9. 最终建议

要保证一阶段召回方向的质量，应采用：

```text
controlled direction ontology
+ chief-problem-specific templates
+ orthogonal partitions
+ residual buckets
+ cannot-miss guardrails
+ rare-disease protected channel
+ direction × evidence matrix
+ salience filtering
+ coverage regression tests
```

最关键的一点是：

> **一阶段的“方向”必须是可被证据区分的病理生理方向，而不是疾病名、综合征名或文档主题。**

判断一个方向是否合格，看三个问题：

```text
1. 它是否覆盖了一类可能解释本次主问题的机制？
2. 它是否与同层其他方向有清楚边界？
3. 它是否至少有一组可用于区分的症状、体征、实验室、影像或病史证据？
```

若答案不是三个“是”，这个方向就不应作为一阶段独立方向；要么合并，要么下沉到第二阶段疾病级鉴别。
