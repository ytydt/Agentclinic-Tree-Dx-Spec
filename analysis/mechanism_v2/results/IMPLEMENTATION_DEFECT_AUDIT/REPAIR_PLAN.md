# 修复工作包与新增语义技术的实施方案

本文件是待实施计划。输入冻结于 `bbc036e8`，没有把本轮复现器接入生产，也没有以人工选定 gold 路由充当自动算法。工作包可分别审查、提交和回放；不要把全部修复捆成一次不可归因的重写。

## 1. 修复分类的实际含义

`code_only` 只表示：在输入已经包含相应正确字段或约束明确时，可以确定正确代码行为。例如遍历所有候选后选择可信 exact，不需要新医学模型；但 source subject 是错的，exact 路由仍会忠实地送到错误疾病。`hybrid_semantic` 表示可以先阻止未获许可的猜测，但补回合法绑定需要更多信息；`design_policy` 表示先确定要实现的语义，再写代码。三者是工程责任边界，不是模型能力高低排名。

## 3. 实施依赖与最小安全子集

C01/C02 先保证能信任实验输入与日志。C03/C04 可在固定输入上并行开发，但进入执行前共同通过身份/引用验收。C05 与阶段补充的数据结构同步。C06/C07 必须共享同一个 EligibilityDecision/RuleExecutionRecord，避免每层各写一个略有不同的过滤条件；C08 只消费已经合格的根证据。C09 修复键与统计谱系后独立消融，不让 corpus lift 掩盖本体/连接修复。

最小上线子集可只接受审核过的原子或浅组，不要求第一版支持所有嵌套量词；但必须可区分“不支持”和“规则为空”，必须保留原文和完整成员引用，不能把复杂规则拆成更强的简单硬规则。删除错误推断通路与提高复杂规则覆盖是两个独立端点。

## 4. 反事实与回归验收设计

固定同一源窗、原始提取、患者事实和候选，依次比较：旧实现；C01–C05 结构/边界修补；C06–C08 语义执行合同；S01 术语；S02/S03 语义恢复。每一步保存完整的原始 ID→规范 ID→member edge→join→literal→root→action→ranking 谱系。病例74、56、49、773等只作为开发回归，不重新称作确认集。

需要同时报告：

- **工程正确性**：配置与缓存隔离、输入排列、重复曝光、引用完备、非法字段、source hash、全部分数与状态可复算。
- **绑定能力**：正确绑定、错误绑定、应绑未绑、歧义、NIL，以及主体/层级/因果/观察事件分项；安全弃权不能掩盖零覆盖。
- **规则保真**：源单位忠实/曲解/遗漏，输出单位无来源幻觉；完整组 package 中矛盾/虚构输出另列，防止多输出撞中一条就算忠实。
- **执行正确性**：有效硬确认/排除召回、错误硬动作、合格软证据与比较方向、非诊断通道污染、未知/冲突/不适用状态。
- **诊断终点**：完整标签、组件、上位/近似标签分别计；真实可共存病与任务所问病因/部位区分。记录候选生成变化与固定池排序变化。
- **成本与稳定性**：实际调用、tokens、重试、缓存命中、弃权及按 source/case 聚类的不确定性；固定配置重复与缓存重放不是同一种重复实验。

来源文档、同义概念族和模板泄漏应独立检查；模型/术语阈值只能在开发样本确定。没有在新确认源/病例上验证前，不应将通过合成夹具表述为达到临床安全阈值。

## 5. 本轮没有交付什么

没有实施这些生产修改，没有生成一批新模型输出，也没有因为某一修补使旧代理 top-3 下降便回退正确性要求。工作包、真实函数反例和主源调研已使下一轮代码实现具备明确范围；真正的改进结论仍需实施后按上述端点测量。
