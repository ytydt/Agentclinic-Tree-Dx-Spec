## 更正记录：原始 `all,n=1` 未穿过历史规范化边界

本次审阅先看到实际 raw 的 `all,n=1,size=2`，结合执行器公式，向根审核员报告了直接坏输入可使单命中置真；初步措辞包含“真实 raw 结构＋代码共同提供可达程序见证”，尚未核对中间产物。根审核员要求继续核验规范化边界后，**生产可达性含义被撤回**，不隐去这次修正。

实际 `normalise_group` 明确在 `logic != at_least_n` 时清空 `n`。直接运行该函数及读取历史保存文件均确认：old/v2 的全局断言2564/2565、free/v2的2235/2236 均已为 `all,n=null`。使用相应v2来源、B1+S7设置的选中两行F7探针也未恢复n=1：old保留两行，new探针保留一行，但均为n=null。**两行探针不等于全病例gate／绑定／去重结果，不能据此宣称new真实组变成singleton。**

可复查脚本为 `audit_all_n1_boundary.py`，产物为 `all_n1_normalization_boundary.json`，含源码/缓存/保存文件哈希、实际来源、局部/全局行号、直接规范化结果、保存对象和F7探针。未重跑实际病例诊断。

最终界限：原始抽取确实把内部“1 main feature”的数字放进外层ALL，但**此数字在历史保存的执行器输入前已清除**。一个一般性的、直接接收未清洗坏输入的执行器仍可能因 `target=need or size` 单命中置真；本例不能证明该缺陷发生于历史生产轨迹。下节的代码绝对表述仍应限定，却不得将这两个raw例子计入生产单命中组满足错误率。

## 一项须修正的概括：`all` 的 `met` 并非永远不能被单成员置真

分类图 §3 第2项原表述“`all` 在只有一个成员命中时，当前代码并没有把 `met` 设为真”过于绝对。它仅对有效目标数 `target > 1` 的通常情况成立。现行 `run_mechanical_engine.py` 的实际计算为：

```python
target = need or size
met = len(sat) >= target and not vio
```

因此一个两成员的 `all` 组只要携带 `n=1`，一个命中且没有已知违反就会使 `met=True`。这不是纯假设：全量账本和原始缓存各有一例 v2 对应结构：

| 臂 | 原始 cache | 局部行号 | 组 | 成员／结构 |
|---|---|---|---|---|
| old/v2 | `af8d1e336c3e8efee9dcd6ac44f19ba64957b0bd` | 2, 3 | g2 | Possible LBD；progressive dementia、1 main feature；`all,n=1` |
| free/v2 | `542d4e51ff20ec4296f25b2f7f562ac3912e823d` | 4, 5 | g2 | 同上；`all,n=1` |

两臂 quote 均为 `Possible LBD: progressive dementia + 1 main feature`。内部“至少/一项 main feature”的计数被放入包含 progressive dementia 的外层 `all`；然后执行器用 `n` 覆盖外层成员数。对于 `progressive dementia=True`、`1 main feature=unknown`、无 `vio` 的输入投影，代码会得到 `target=1, met=True`。

**原初判断（生产可达性含义已由上节撤回）**曾为“真实 raw 结构与代码共同提供可达程序见证”。最终只支持直接坏输入的条件性质；实际规范化已清除n=1，故不是历史执行器单命中置真的实例，更不是实际误确诊计数。

建议修改：先写“对正常 `target=size>1` 的 all 组，单命中可产生部分正分而不使 met 为真”，再补充“执行器若直接收到未规范化的 `all,n=1,size=2`，因 n 覆盖 size 可单命中置真；发现的历史raw例子已在规范化中清除n，不能证明生产发生”。主报告现有“代码未必把 met 置真”相对谨慎，但可同时加上此更完整分型。

## 两处代码条件应写全

1. 分类图中“用任何成员的 required 触发必要性”应写为：**任一成员同时 `relation=required_for` 且 `modality=obligatory` 时置 `required=True`**。单独 `required_for/typical` 不满足这个门槛。
2. F4b 开启时确实对任意 `logic=all` 置 `required=True`，但触发硬排除还要求出现 `vio`，且组并非完全属于 `SOFT_CONTEXTS`。在 closed-world 模式下，未匹配成员还可能被改放进 `vio`。报告应区分“内部 required 标志被设置”和“该运行实际发出硬排除”。

上述补充不改变 `all` 不能推出疾病必要性的核心批评。
