# 读者指南：机械规则链七份审计的共用术语

这七个目录记录的是同一条流水线的审计。它们互相引用、共用一套简写，而这套简写从没在任何一处完整定义过。本文用平实语言把它们讲清楚，**面向没参与过本仓库开发的读者**。

各目录自己还有一份 `EXPLAINER.md`，讲那个目录独有的东西。本文只讲跨目录共用的部分。

---

## 一、先搞清楚被审计的东西是什么

有一条流水线，目标是**给一份病历排出最可能的诊断**。它分五步：

1. **语料**：把临床指南、教科书、综述切成小段（chunk）存起来。
2. **检索**：给定一个病例和一个候选诊断，找出最相关的若干段文字。
3. **抽取**：让一个大语言模型读这些文字，吐出结构化的「断言」，例如「布鲁氏菌病 —— 需要 —— 血清学阳性」。
4. **门闸**：一批程序规则，把明显不合格的断言降级或丢弃。
5. **引擎**：把断言和病人实际的检查结果对起来，给每个候选诊断打分排名。

这七份审计分别在问：语料对不对、抽取忠不忠实、门闸讲不讲理、引擎执行得对不对、以及**我们用来衡量它的那把尺子本身可不可信**。

最后一条是这批交付里分量最重的发现。

---

## 二、断言长什么样

一条断言是一个结构化的句子，主要有这些槽位：

| 槽位 | 含义 | 例子 |
|---|---|---|
| `subject` | 这条规则说的是哪个病 | `Brucellosis` |
| `predicate` | 说这个病的什么表现/检查 | `positive serology` |
| `relation` | 两者是什么关系（见下） | `required_for` |
| `polarity` | 说的是「有」还是「没有」 | `asserted` / `negated` |
| `modality` | 语气强弱 | `obligatory`（必须）/ `typical`（通常）|
| `threshold` | 数值门槛 | `> 2 %` |
| `quote` | 这条断言依据的原文片段 | `"Evidence of ischemic..."` |
| `criterion_group` | 它是不是某个「判据组」的成员（见下） | `{group_id: g1, logic: all}` |

### relation：关系类型

engine 只对其中四种给「硬」待遇，其余都只是加权计分的软证据：

| relation | 意思 | 引擎怎么用 |
|---|---|---|
| `required_for` | 没有它就不是这个病 | 明确为假 → 淘汰该候选（层一）|
| `excludes` | 有它就不是这个病 | 为真 → 淘汰该候选（层一）|
| `pathognomonic_for` | 有它就基本可确诊 | 为真 → 确认（层二）|
| `sufficient_for` | 有它足以诊断 | 为真 → 确认（层二）|
| `feature_of`、`caused_by`、`treated_by`… | 一般关联 | 只加分（层三）|

`argues_against` 名义上是「不支持」这种可推翻的弱证据，但**代码里它和 `excludes` 走同一条无条件否决分支**（见反例 E15）。这是审计反复指出的问题之一。

### criterion_group：判据组

指南常写「以下四条满足两条即可诊断」。抽取器会给这几条断言同一个 `group_id`，并标注：

- `logic = all`：全部满足
- `logic = any`：任一满足
- `logic = at_least_n` 配 `n`：至少 n 条

**注意**：这套结构只有一层，无法表达嵌套（例如「A 且（B 或 C）」），也无法表达计分表（「这项 +2 分、那项 −1 分，总分 ≥6 分即诊断」）。指南里大量规则属于后两类。这是「schema 表达力不足」这个说法的具体所指。

## 三、引擎的四层

对每个候选诊断依次走：

| 层 | 干什么 | 结果 |
|---|---|---|
| **层一** | 硬否决 | 触发就把这个候选淘汰出局 |
| **层二** | 硬确认 | 触发就直接认定 |
| **层三** | 加权求和 | 每条软证据加一点分 |
| **层四** | 收尾 | 竞争扣分等调整 |

判据组在层一之前单独求值，整组只贡献一次分，而不是每个成员各加一次。

**排序键不是单纯的分数**，而是「是否被淘汰 → 确认条目数 → 分数」三级。所以一个 0 分候选可能排在一个 25 分但被淘汰的候选前面。这点在读排名表时极易搞错。

## 四、接合（join）：断言怎么和病人对上

断言说的是 `positive serology`，病历里写的是 `Brucella agglutination titre 1:320`。要判断这条规则是否被满足，必须先把两个字符串对起来。这一步叫 **join / 接合**，有六种方式，按可靠度从高到低：

| 方式 | 含义 |
|---|---|
| `exact` | 完全一致 |
| `containment` | 一个包含另一个 |
| `overlap` | 词有重叠 |
| `marker` | 共享一个标记物词元（CD34、p63 这类）|
| `loose` | 宽松词面匹配 |
| `embed` | 句向量相似度超过阈值 |

**关键实现细节**：`embed` 不是现场调用编码器，而是查一张**冻结的表** `join_embeddings.npz`，键是精确字符串。查不到直接返回 0。四个实验臂的谓词命中这张表的比例分别是 59.5% / 50.2% / 50.3% / 43.8%——**换了语料或提示词产生新措辞的臂，覆盖率系统性更低**。所以名义上相同的阈值并不等于各臂拥有同等的接合能力。

全流水线的接合率约 **17%**：每 6 条绑定到候选的断言，只有约 1 条能碰到病人的某个发现。

## 五、实验臂的命名

一个 2×2 实验，两个因子：

- **提示词**：`old`（旧，限定判据组必须在同一句内）vs `free` / `new`（新，允许成员跨行跨句）
- **索引**：`old`（旧语料索引）vs `v2`（修复过入库缺陷的语料索引）

四个臂的别名：

| 别名 | 含义 |
|---|---|
| `old_old` | 旧提示词 + 旧索引 |
| `free_old` = `new_old` | 新提示词 + 旧索引 |
| `old_v2` | 旧提示词 + v2 索引 |
| `free_v2` = `new_v2` | 新提示词 + v2 索引 |

`free_*` 和 `new_*` 是同一批数据的两个叫法，**不表示又生成了一批新数据**。

## 六、配置代号：B1、S7、F1–F10、E1–E17、G1–G3

这是最容易劝退读者的一套简写，而且**存在跨文档撞车**。

### B1 / S7

- **B1**：基线配置，`{权重=idf, 接合=loose, 判据组=开}`。
- **S7**：在 B1 上叠加的一组修复，`{embed_tau=0.6, marker, organism, enum_clamp, corpus_lr, group_all_required, quote_gate}`。

「B1+S7」＝主报告里所谓的「交付配置」，绝大多数排名数字都是在它下面测的。

### F 系列：引擎侧开关

| 代号 | 作用 |
|---|---|
| F1 | 语料似然比加权 |
| F2a/F2b/F2c | marker 接合 / 句向量接合 / 句向量需词面锚定 |
| F3 | 病原体词干归一（Brucella ↔ Brucellosis）|
| F4b | 把 `all` 组当作该病的必要条件 |
| F5a | 把实为「上下文类型」的 relation 夹回合法枚举 |
| F7 | 引文门闸：断言若曲解自己的 quote 就降级 |
| F8 | 可选路径，未进入冻结四臂 |
| F10 | 同一发现重复投票的阻尼，**默认关闭** |

### E 系列：⚠ 两套不同的 E 编号

这是本批文档最危险的一处撞车：

- **主报告的 E1–E17** 指**门闸规则**（`gate_assertions.py` 里的降级规则）。例如主报告 **E17** ＝「asserted 的 `excludes` 若引语没有排除线索，降级为 `feature_of`」。
- **`POST_V2_RULE_SEMANTICS_AUDIT` 的 E01–E26** 指**引擎语义反例**（27 个合成见证）。例如该目录的 **E17** ＝「基数计的是行数不是不同判据」，和主报告的 E17 毫无关系。

对应关系里最重要的一条：**该目录的 E23 ＝ 主报告的 E17**（都在说门闸放行了没有排除依据的 `excludes`）。读的时候必须先看清是哪一套编号。

### G 系列

`G1`/`G2`/`G3` 是门闸里的三条改写规则（对偶槽位、参考范围、连词肢）。注意 `g1`/`g2` 小写还可能指**抽取器给某个 passage 内判据组起的局部编号**，两者不是一回事。

## 七、gid、oracle_gids 与「跨索引不可比」

- **gid**：语料索引里某个 chunk 的**行号**。
- **oracle_gids**：人工标注的「这道题的答案应该在这几个 chunk 里」。

**陷阱**：gid 是行号，不是稳定 ID。旧索引 861,131 行，v2 索引 907,371 行，同一个整数在两个索引里指向**完全不同的文字**。所以任何 gid 都必须连同索引版本一起用，跨索引直接比较会得到看似灾难性、实则毫无意义的结果。（主报告曾因此误报「oracle 召回掉到 11/26」，实为伪影。）

## 八、这批审计里最重要的一组概念：金标口径

主报告长期使用的 top-1 / top-3 / MRR，判定「答对」的依据是一个叫 `gold_labels_in_set` 的**代理集合**，它接受父类和组件。这批审计把它和严格口径分开了：

| 口径 | 含义 | 11 例上的表现 |
|---|---|---|
| **legacy / 代理金标** | 接受父类、组件、甚至错误实体 | top-3 = 7/11 |
| **explicit complete label / 完整标签** | 候选池里存在与金标完全对应的标签 | 只有 **5/11** 例存在；top-3 = 4/11，top-1 = 1/11 |

代理口径宽到什么程度：

- 例 91 金标是 **Angiosarcoma**（恶性），代理接受 **Hemangioma**（良性）——**实体是错的**，不是可接受的父类模糊。
- 例 56 金标是 Spindle cell squamous cell carcinoma，代理接受泛化的 **Carcinoma**；真正完整的标签排在第 21–22 位。
- 例 522 金标是「路易体痴呆导致的紧张症」，代理接受单独的 **Catatonia**（只是组件）。
- 例 773 金标是「IPAH 合并 PFO」，代理接受单独的 **PFO**。

所以「7/11」不能读作「七例诊断成功」。它是 **4 个完整标签命中 + 3 个父类/组件命中**。

## 九、重复候选：一个会污染所有排名数字的缺陷

同一个疾病概念在候选列表里出现**两次，只差大小写**（例如 `Catecholaminergic Polymorphic Ventricular Tachycardia` 和 `Catecholaminergic polymorphic ventricular tachycardia`）。

引擎的 `subject_match` 一旦匹配到第一个候选就停止，所以**全部证据落到其中一个身上，另一个成为 0 分空壳**。但那个空壳仍然占据一个排名位次。

后果：

- 一个**被淘汰**的概念，可以通过它的空壳双胞胎在排名里「存活」到更靠前的位置。
- 报告出来的「金标名次」可能来自那个空壳，而不是真正拿到证据的那个节点。

11 例里 **9 例**有这种重复（共 23 组），其中 10 组出现了证据分裂，2 组重复的正是代理金标。

## 十、读这批文档时要守住的几条边界

这些是各目录 README 自己写明的限制，读者务必带着它们看结论：

1. **「AI 审阅」不是「临床专家审阅」。** 所有语义判定由 AI 审计代理完成，多处明确声明未经人类临床医生双盲复核。
2. **合成反例不是发生率。** 27 个引擎反例是构造出来隔离机制的，证明「这个缺陷存在且可复现」，**不证明它在真实病例中发生了多少次**。
3. **「可复现旧行为」≠「已修复」。** 复现脚本通过，意思是所描述的缺陷仍在，不是缺陷已被解决。
4. **11 例是开发集，不是确认集。** 它被反复使用过，只能用于回归和溯源，不能当作新方案的独立验证。
5. **干预不可相加。** 「只删数值」「阻断接合」「整行删除」三种干预的估计对象不同，不能互换，也不能把各自的 MRR 差相加当成因果分解。
6. **样本量。** 来源侧 286 条规则、输出侧 180 个单元、11 个病例。所有区间只含抽样误差，不含审阅判断误差。
